How it works

One hub, one agent per server, and nothing in between.

{{- partial "how-it-works.html" . }}
  1. Start the hub. On first start it creates its SQLite databases and a self-signed certificate for the agent channel.
  2. Add a node. The dashboard gives you a join token that works once, within an hour. It carries the fingerprint of the hub's certificate.
  3. Run the agent. It dials the hub over TLS 1.3 on port 55001, checks the certificate against that fingerprint, and saves its own key for next time.
  4. Watch. Stats arrive every five seconds, and the dashboard charts them.

You stay in control

Each project on a server carries a config.vpspilot.json, written by whoever owns the server. It's the complete list of what the dashboard may ever do with that project.

The hub sends names, never command strings. To run build, it sends the agent the word "build". The agent looks that name up in the file on the server and runs the command written there. Even someone who took over your hub couldn't run anything that isn't already in a file you wrote.

Running commands is coming soon. Today the dashboard shows what each project declares.

What it's not

VPS Pilot watches your servers and does what each project allows. It doesn't try to be a platform.

Those jobs have good tools already: Coolify or Dokploy for Git deploys and containers, Ansible for provisioning, and plain SSH for the rest.

Built small

One hub binary, one agent binary, and no external services: no separate database server, no queue, no cloud account.

Go

The hub: the API, the agent channel and the dashboard in one executable.

Rust

The agent: a single binary on each server.

SQLite

Two database files in one data directory, with a pure Go driver.

React

The dashboard, built with Vite and embedded in the hub.
